# SDK 按需会话同步改造说明

状态：设计方案，尚未实现或完成端到端验证。日期：2026-09-08。

配套服务端方案见 [server-conversation-sync-plan.md](server-conversation-sync-plan.md)。服务端已实现的项目自有 V2 接口见 [接口与联调说明](server-conversation-sync-v2-implementation.md)，完整字段以服务端 `pkg/syncv2/pb/sync.proto` 为准；这些不是官方 SDK 或原 PR 已有能力。本文的 SDK 修改仍未实施。

## 1. 目标与已核对基线

目标：新设备登录时，只同步服务端选定的会话详情和消息；已有设备保留本地历史记录；被排除的会话可以通过新消息、置顶、主动打开重新加载。

已检查官方 SDK Core：

- 核对时最新发布版 `v3.8.3-patch.15`，实际代码提交 `d6e0b549db904d0327d76ef7c9c283203879a095`（附注标签对象为 `b5544458aebeb737d75b2627bb12f9e73b2a1ea5`）。
- 检查时主分支提交 `9267a252faab02bbc8ffab6223e6ae2341a0f7c9`。
- 两者均存在下述绕过 ID 过滤的路径。实际 Android/iOS/Flutter/Web 封装应确认所绑定的 Core 提交；Mini Web 不在此次 Core 核对范围内。

当前流程：

1. `IncrSyncConversations` 触发全量时，通过 `get_owner_conversation` 分页拉详情，或者调用 `get_all_conversations`。
2. 详情同步之后调用 `get_full_conversation_ids`，将结果保存到版本记录的 `UIDList`。
3. `SyncAllConversationHashReadSeqs` 不传 ID 列表，获取全部会话序号，并补回本地不存在的会话。
4. `internal/interaction/msg_sync.go` 还独立调用 `GetMaxSeq`；服务端该接口枚举所有会话及通知会话。

因此不能只修改全量 ID 请求，也不能只改会话列表，必须同时约束详情、已读序号、普通消息补拉三个入口。

## 2. 能力协商与契约

服务端已新增 `/conversation/sync_capabilities` 能力协商与 `/conversation/sync_snapshot` 接口。首请求包含 `userID`、`pageSize`、`scope`，续页包含 `snapshotID`、`cursor` 且同一 scope 不改变页大小；服务端返回：

启用策略：不设置灰度账号、账号白名单或全局开关。服务端版本和 SDK 均支持 V2 时，所有用户自动进入新流程；不支持 V2 时维持旧流程。能力协商只用于协议兼容。会话数量阈值只影响过滤规则，SDK 不按账号做特殊分支。

| 字段 | 含义 |
| --- | --- |
| `snapshotID` / `expiresAt` | 本轮固定 ID 集合及有效期 |
| `cursor` / `hasMore` | 不透明游标与是否还有下一页 |
| `conversationIDs` / `total` | 当前页 ID、快照总数 |
| `policyVersion` | 本轮过滤策略版本 |
| `versionID` / `version` | 创建快照前记录的会话增量基准 |
| `mode` | `filtered` 或 `full`（≤5000，不过滤但仍使用 V2） |
| `scope` / `includeSelf` | `chat` 或 `notifications`；通知首轮需同步自通知 |

字段名、鉴权和错误码已在实现说明中锁定。客户端不能把页号当作数据库偏移，也不能用 `total` 代替 `hasMore` 判断结束。

接入必须使用 `/msg/sync_seqs_v2` 的 `includeDetails=true` 获取带最新边界的详情；空集合即空。通知请求传父会话 ID，返回实际通知流 ID，消息请求仍用父 ID。自通知单独请求，避免与 500 个父 ID 同批超限。消息请求使用 `/msg/sync_messages_v2`，携带对应 `stateToken`；当前策略 `conversation-sync-v2.2` 的令牌只表示流 ID、最小可见序号和 `permissionMaxSeq` 权限上限（0 为无额外上限），不是事件版本。新消息增长/已读推进不使令牌失效，`STATE_CHANGED` 后应重查状态；不能用令牌排序响应，仍须在清空/权限事件后作废旧在途任务。

`known=false` 表示尾消息/边界未确认，不能据此提交最终未读或宣告历史范围完整；消息响应的 `unresolvedSeqs` 不是已删除消息。保留待校验任务、退避重试；预分配空洞可能长期存在，初始界面可用与后台历史完整性应分开，不要无限阻塞登录或无限即时重试。普通/通知两套分页完成或任务取消后，调用 `/conversation/sync_snapshot_release` 释放配额，失败时让 TTL 兜底；创建响应丢失不要无限重复创建。

这是超出原 PR #3740 的双端设计。开发前同时锁定可见序号边界、未读计数口径、通知类型及状态版本机制；明确区分协议不支持、快照失效、无权限/真实删除与可重试故障，不能仅凭 HTTP 状态或空响应推断数据已删除。

注意：该快照只固定 ID 集合，并非数据库跨表事务快照。完成后必须追赶会话增量及消息变化；消息送达本身不一定增加会话元数据版本。

错误处理：

- 明确返回不支持能力：本轮进入旧流程。
- 快照过期：保留本地状态，重新申请快照，去重后续传或重跑。
- 超时、限流、鉴权失败：分别重试/退避/终止，不直接解释为“不支持”并全量重拉。
- 真正为空：`mode=filtered`、`total=0`、`hasMore=false` 是成功结果，不触发旧接口兜底。

## 3. 首次同步流程

1. 协商能力；不支持时走现有流程。
2. 获取并暂存本轮全部快照 ID，逐页校验同一 `snapshotID`、用户及策略版本，ID 去重。
3. 按 ID 分批拉取会话详情，建议每批 300 个，并遵守服务端公布的数量和字节上限。
4. 本地以 upsert 合并详情。同步完成前不执行 `DeleteAllConversation`，不因快照未包含某 ID 而删除它。
5. 对选中集合分批查询已读/最大序号；空集合直接跳过普通会话请求。现有接口的空 ID 表示“全部”，不能误调用。
6. 初始化选中会话的普通消息同步范围。修改 `interaction/msg_sync.go` 的首次和重连路径，使其不再重新取得全库普通会话序号。
7. 独立同步通知流，并处理快照创建后收到的新消息、元数据变更及激活事件。
8. 追赶快照基准之后的增量；服务端要求重新全量时，重新进入本流程，不能落回无过滤的 `FullSyncer`。
9. 各阶段成功后才提交对应完成标记和版本游标。重启后可重试，不能用较新的游标跳过尚未落库的数据。

批次允许顺序执行，后续按实测增加有界并发。不要为每个会话启动一个 goroutine。部分会话无权限/已删除需使用服务端明确结果处理，批次网络失败不能视为删除。

## 4. 本地数据模型与删除语义

增加独立的同步选择状态，至少记录 `userID`、`policyVersion`、快照进度、选中 ID，以及同步阶段。不要将旧版本记录 `UIDList` 直接改作所有业务通用的过滤白名单。

- `selected`：本轮加载普通消息的会话。
- `deferred`：暂未加载的会话，不代表服务器删除。
- 服务端明确的 `delete/tombstone`：按既有删除语义处理。

已有设备保留本地详情、草稿及消息；字段更新不得用服务器默认值覆盖本地草稿和展示状态。本次不默认清空旧设备已显示的历史列表，因此主要收益是新设备/重装同步。

带本地草稿的会话即使未入选，也必须保留草稿及入口。服务器不知道未上传的草稿，SDK 不得依赖快照替自己保留它；新设备不承诺恢复未上传草稿，本次不增加云端草稿同步。

### 未读数

与服务端共用可见边界和计数语义。最小可见序号 L 为包含边界、最大可见序号 U、已读序号 R 时，连续序号基础计数为 `max(0, U - max(R, L - 1))`，L > U 时为零。实现前确认零值、非连续序号、撤回/删除、通知及免打扰的既有规则，不能机械套用公式改变业务口径。

不得直接用原始 `maxSeq - hasReadSeq` 将已清空范围计入；总未读应与各会话按既有规则贡献的计数一致。边界未知时保留待校验状态，不凭缺失字段确认零未读。

若未来要求旧设备也隐藏历史会话，应另加展示层策略，不复用物理删除操作。

## 5. 恢复、离线与通知

### 新消息

选中集合不能成为永久白名单。未知会话收到有效新消息时，按当前权限获取详情并 upsert、加入本地选中集合，初始化其消息序号后拉取允许访问的历史。

### 离线后恢复

仅靠在线推送不足以保证恢复。V2 重连应重新获取服务端选择集合（包含当前未读会话），与本地已加载集合合并；同时追赶通知。若只采用增量激活流，则服务端必须提供可重放的持久化游标，这不是 PR #3740 的现有能力。

### 置顶、主动打开

置顶事件或显式打开应触发按 ID 的服务端详情获取。现有 `GetOneConversation` 在本地不存在时会构建本地记录，不能单凭该调用认定已恢复服务端权限边界和完整元数据。

### 通知流

好友、群成员、权限变化、自通知及被延后会话相关通知不得被普通聊天会话过滤误伤。通知可以更新状态，但不应无条件拉回全部历史聊天。通知父 ID 使用 `scope=notifications` 单独分页，保留既有通知消费进度。服务端升级 MsgTransfer 后持久化退群/被踢/解散的截止序号，离群者可读到终止事件本身，不能读之后的流；旧事件没有截止记录时可能返回不可用，不能当作删除本地通知的指令，仍需现有群成员/好友增量与自通知收敛。本次未实现旧截止数据回填。

| 事件 | SDK 行为 |
| --- | --- |
| 有效新聊天消息、置顶、主动打开 | 校验权限并恢复会话，加入加载集合 |
| 普通资料更新、已读通知 | 更新已存在记录或轻量同步状态；不创建展示会话，不触发历史补拉 |
| 清空、真实删除、退群/权限变化 | 即时更新边界或失效记录，取消不再允许的拉取；不作为恢复触发器 |

### 历史消息入口

本地搜索只覆盖已下载消息。提供独立的服务器历史查询入口，明确结果范围；按权限分页查询，打开具体会话时再恢复详情和允许访问的历史。不能把本地搜索无结果解释为服务端记录已丢失，也不能为搜索自动全量下载全部会话。

## 6. 分页一致性和策略切换

- 同一快照内 ID 顺序、总数稳定，重复取页幂等；分页期间新消息通过后续追赶合并。
- 中断后先检查快照有效期；失效后重建，已落库数据保留。
- 服务端版本回退后，客户端确认不支持 V2，再进入旧流程并安排受控的全量补齐；不得沿用过滤后的完成状态跳过补齐。混合版本部署期间重新协商并固定本轮模式，避免反复切换。仅重连不保证自动补回。
- 降级前停止当前 V2 调度，避免新旧流程并发覆盖版本或重复触发登录完成回调。
- 同步进度按阶段计算，完成通知应只发一次；错误不得表现为同步成功。

多设备并发必须处理：设备 A 正在分页时，设备 B 标记已读、清空或退出群聊。A 在本轮完成前追赶相关事件并重新确认状态；不能认为元数据增量版本已覆盖所有已读/清空变化。

具体实现应按会话串行合并，记录服务端可比较的状态版本/删除标记；收到更新后，较旧的在途详情和消息响应不能覆盖最新状态或复活已清空数据。若现有事件没有足够版本信息，需要补充协议或使在途结果失效后重新读取，不能用设备本地时间猜测先后。

权限和可见范围变化在服务端提交后约束后续读取；SDK 一旦获知立即处理，不等快照过期。离线设备无法实时获知变化，恢复连接后必须先追赶或校验边界再应用旧请求结果。标记已读和清空/权限限制须按各自规则处理，不可把所有变化统一成序号取最大值。

## 8. 验收用例

1. 50,000 会话中 45,000 已读且闲置、5,000 应保留：详情及普通消息序号请求只覆盖应保留集合；通过抓包/请求日志证明没有其他全量路径绕过。
2. 5,000 与 5,001 阈值；置顶、未读、已清空、空会话、活动时间未知分别验证。
3. 服务端返回空集合：普通序号请求次数为零，通知继续同步，正常完成登录。
4. 连续翻页期间消息到达、置顶、删除：不永久漏会话，不复活真正删除的记录。
5. 断网、进程退出、快照过期、重复页面：无已存在记录丢失，进度可恢复。
6. 旧设备升级：本地历史消息、草稿、置顶展示不因被延后而被删除。
7. 未加载会话在线/离线收到消息、置顶或主动打开：权限正确、可恢复、无重复记录。
8. 新 SDK + 旧服务器、旧 SDK + 新服务器：维持旧行为；新 SDK + 新服务器才进入 V2。
9. 服务端版本回退后补齐成功；混合版本期间模式不反复切换；重连不重复全量同步；群/好友同步无回归。
10. 覆盖退群后的可见序号上限、清空后的最小序号、通知流及总未读数。
11. 已清空但旧已读序号滞后：会话与总未读不包含已清空范围；个人最大可见序号截断后计数正确。
12. 设备 A 分页，设备 B 标记已读/清空：A 正确收敛；模拟旧消息响应晚于清空通知到达，已清空消息不复活。
13. 分页期间真实删除/退群：后续读取遵守最新权限和可见范围，较旧详情响应不能覆盖新状态。
14. 暂未加载会话连续收到资料更新/已读通知：不新增展示会话、不触发历史消息补拉；有效聊天消息、置顶、主动打开仍可恢复。
15. 有草稿的已有会话被排除：草稿和入口保留；新设备不会虚构未上传草稿。
16. 本地搜索找不到未下载消息时，服务器历史查询可按权限返回结果；查询不会触发全量历史下载。

真实性能验收分别测冷/热缓存、多账号并发；记录登录完成耗时 P50/P95/P99、各接口请求量/字节数、内存峰值、数据库操作数。原 PR 的模拟基准不作为上线压测结论。
