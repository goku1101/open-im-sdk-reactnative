# 服务端按需会话同步方案

日期：2026-09-08。状态：服务端 V2 源码及本地真实依赖联调已落地，尚未部署/接入 SDK。配套 [SDK 修改说明](sdk-conversation-sync-plan.md)；已实现的接口、限制、测试和剩余验收见 [实现说明](server-conversation-sync-v2-implementation.md)。下文保留设计目标，实际契约以实现说明和 `pkg/syncv2/pb/sync.proto` 为准。

## 1. 决策

采用 PR #3740 的过滤思路及独立全量序号查询能力，建设能力协商后的 V2 同步流程。保留旧接口语义，不直接对所有客户端启用原 PR 的过滤。最新官方 SDK 仍通过详情全量同步、已读序号同步和独立消息同步绕过 ID 过滤，服务端单独上线不能承诺解决登录慢。

不设置灰度账号、账号白名单或全局开关。新服务端部署完成后，支持 V2 的 SDK 自动使用新流程，重点优化新设备。旧版 SDK 继续原有流程；旧设备本地记录不主动删除。5,000 条阈值只决定是否过滤，不决定账号是否能使用 V2。

## 2. 过滤与权限

历史会话总数 > 5,000 才启用，闲置阈值默认 30 天；均可配置。

1. 鉴权和真实删除/退群可见范围优先，不能用置顶绕过权限。
2. 可访问的置顶会话保留。
3. 非置顶空会话、用户已清空的会话排除。
4. 其余仅排除已读且最后可见消息时间早于阈值的会话。
5. 序号/时间无法可靠判断时保留，不把缺失数据当作零或已删除。

用户有效最大序号需考虑个人 MaxSeq 上限；已清空判断采用 UserMinSeq > 有效 MaxSeq。用于活动判断的时间应对应用户可见消息，不能使用退群后其他成员最新消息的时间。

过滤只决定本轮同步选择，不删除消息和会话。每个按 ID 查询都重新验证当前访问权限。

### 未读数口径

服务端与 SDK 使用相同的有效可见序号边界。若最小可见序号 L 为包含边界、最大可见序号为 U、已读序号为 R，则连续序号计数的基础值为 `max(0, U - max(R, L - 1))`；L > U 时为零。实现前核实当前存储边界定义、零值含义，以及撤回、删除、通知和免打扰的现有计数规则，不能直接把公式当作最终业务口径。

会话未读和总未读必须一致；禁止因未加载会话而遗漏应计入的未读，也不能直接累加原始 `maxSeq - hasReadSeq` 将已清空范围计入。未知边界不得作为已读依据。

## 3. 接口契约（拟新增）

- 能力 `conversationSyncV2`：通过能力响应声明服务端版本是否支持该协议、策略版本和服务端限制；这是版本兼容信息，不是按用户或全局控制的功能开关。
- `/conversation/sync_snapshot`：首请求创建固定 ID 集合，后续用用户绑定的 `snapshotID + cursor` 分页；返回总数、过期时间、模式、策略版本及增量基准。
- 详情：复用按 ID 查询，SDK 分批，服务端校验数量/字节上限。
- 普通序号：通过 V2 显式集合或快照游标查询，空集合必须表示空。已有“空 ID 表示全部”的接口不更改语义。
- 消息同步：新增或扩展能力协商后的序号入口，覆盖 `GetMaxSeq` 所在链路。普通聊天与通知范围分离；未适配的旧入口继续旧行为。

V2 快照与配套同步契约是本项目新增设计，超出原 PR。双端开发前须锁定请求/响应字段、可见边界定义、错误码及重试语义，并明确区分“不支持协议”“快照失效”“无权限/真实删除”和普通网络故障。

不要仅按 offset 对实时过滤结果翻页。快照初始 TTL 建议 10 分钟，配置化；同一快照固定排序和 total，过期返回明确错误。绑定用户及会话授权上下文，并限制每用户/全局快照数量和内存。

创建前取得增量基准，扫描后客户端追赶增量。快照不是跨表事务：消息到达、权限变更、清空等并发情况需要通过事件和再校验收敛。重连重新取得选择集合，覆盖离线期间变为未读的会话。

## 4. 查询实现

内部 RPC、MongoDB `$in` 和 Redis 批次初始上限 500，增加序列化字节上限与有界并发。RPC 查询集合必须去重。

- 只投影过滤必要字段：会话 ID、置顶、个人序号边界；避免搬运完整会话 Ex 等大字段。
- 已读、UserMinSeq、最大序号缓存批量读；miss 采用批量持久化查询。
- `GetMaxSeqsWithTime` 当前缓存 miss 会逐个回源，不能直接照搬到大账号快照扫描。
- 当前缓存时间不是可靠持久化的消息时间。先对可见最后消息做批量投影回查；若现有数据布局无法提供可接受的批量计划，应新增最后消息摘要并回填，不能伪装成一次廉价批量查询。
- 消息摘要若采用异步更新，未知/落后状态保守保留；不可仅依赖最终一致的旧摘要过滤正在活跃的会话。
- 检查现有单值和批量序号缓存的编码契约，保持同一 key 的兼容性及更新失效行为。

索引变更必须基于真实查询 explain 决定；实施前检查现有索引。压测前确认实际查询次数随批次数增长，不随会话数逐条增长。

## 5. 通知与会话恢复

通知流不能直接套用普通会话过滤；好友、群权限、自通知等仍需完整追赶。大量通知序号采用单独分页/批次，避免一个巨型响应。

在线新消息可触发按 ID 加载。离线恢复采用重新获取选择集合加现有通知追赶，不能只依靠无持久化的在线推送。置顶、主动打开支持按 ID 恢复元数据和受权限限制的消息。

| 事件 | 对暂未加载会话的处理 |
| --- | --- |
| 有效新聊天消息、置顶、主动打开 | 按当前权限恢复详情，加入加载集合 |
| 普通资料更新、已读通知 | 只更新必要状态，不自动加载历史聊天 |
| 清空、真实删除、退群或权限变化 | 立即更新可见边界/失效状态，限制后续读取；按业务语义处理本地数据，不默认恢复会话 |

多设备并发时，设备 A 分页期间设备 B 标记已读或清空，A 完成前须追赶相关事件并重新确认已读和可见边界。会话元数据版本不保证覆盖已读和清空变化，需锁定独立事件/状态版本机制。已提交的清空、删除和权限变更不得被旧快照授权覆盖；后续读取按最新状态校验，不等待快照 TTL。客户端收到失效事件后也必须拒绝较旧的在途响应覆盖新状态。

### 草稿与历史入口

本地草稿不在服务端过滤依据内，SDK 应保留已有设备的草稿及会话入口；本次不增加跨设备草稿同步，新设备不承诺恢复未上传草稿。

明确区分本地消息搜索与服务器历史查询。新设备未下载的数据不能通过本地搜索找到；客户端提供显式查询服务器历史的入口，服务端复用或补齐带鉴权、分页和可见边界校验的查询。历史查询不自动恢复全部历史会话，用户打开具体结果时才按 ID 加载。

## 6. 自动生效、故障与版本回退

拟议配置：threshold=5000、inactiveDays=30、batchSize=500、snapshotTTL=10m、并发/速率/超时限制、policyVersion。不提供 enabled 或按账号启用的配置。阈值、时长、批次和 TTL 必须为合法正值，不能约定特殊值充当关闭功能的入口。

能力不支持可走旧流程；瞬时错误返回明确可重试结果，不在每次错误时自动触发巨型全量查询。若提供旧模式回退，应显式协商、限流，并支持旧路径分页。

回滚通过服务端版本回退完成。先回退对外 V2 API/相关网关，再回退 Conversation RPC，最后回退 Msg RPC，避免对外仍声明支持 V2 而下游已经不支持。SDK 在确认服务端不支持 V2 后停止本轮任务、进入旧流程并发起受控补齐，不能只切换模式而沿用过滤后的完成状态。混合版本期间遇到不支持响应应重新协商并固定本轮模式。已签发快照无法继续时需重新同步，不能在续页时偷偷改变集合。

## 7. 实施与上线顺序

1. 固定协议改动到可控仓库；定义 V2 类型/能力、缓存契约及双端用例。保留现有定制功能。
2. 实现批量查询、快照及通知分离；相关边界单测和真实依赖集成测试通过。
3. MsgTransfer 全实例更新 → Msg RPC 全实例更新 → Conversation RPC 全实例更新 → API/涉及协议的网关更新；先持久化离群通知截止序号，再开放 V2 读取。回滚按反序执行，最后回退 MsgTransfer，保留截止集合。
4. SDK 接入并通过混合版本、冷缓存、离线恢复和回滚联调。
5. 上述联调先在测试环境验收通过，再按顺序发布生产版本。生产部署完成后，所有支持 V2 的 SDK 自动进入新流程；需要回滚时执行版本回退和客户端受控补齐。

上线门槛：5 万会话冷/热缓存测试、并发登录测试、过滤正确性、通知完整性、非好友私聊和 Push 组合回归通过；明确登录耗时预算和回退阈值后执行。已有 PR 模拟基准只能证明响应缩小，不能证明生产性能。

补充双端验收：清空后已读序号滞后仍为零未读；个人可见上限影响未读计算；多设备在分页期间标记已读/清空/退群，最终状态正确且旧响应不能覆盖；普通资料/已读通知不恢复历史会话；有效新消息可恢复；已有设备草稿保留；本地搜索与服务器历史查询结果范围清晰，服务器查询遵守最新权限。

## 8. 交付边界

服务端已实现自有 V2 协议、固定快照、批量状态/详情、普通/通知分离及受权限限制的消息读取，并通过本地真实 Mongo/Redis/gRPC 验证；不再依赖未发布协议镜像。本次审查修复将权限令牌与实时尾/已读状态分离，加入快照内部自适应拆批；新增 `sync_v2_notification_boundary` 集合（使用内置主键索引）记录退群/被踢/解散的通知截止序号。没有历史回填，升级前缺少截止记录的离群用户仍不能补拉旧群通知。SDK 改造、RN 原生构建、完整 Kafka 故障恢复、端到端验收和部署仍待完成。具体完成项与限制见实现说明，不将本地测试视为生产上线验收。
